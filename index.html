OpenThinking
pipelines de IA como código.

Un orquestador en el que varios LLMs colaboran sobre una misma tarea, con contexto compartido, permisos y herramientas. Definido en YAML. Ejecutado desde tu terminal.

TypeScript + Bun CLI-first github.com/sicora-dev/open-thinking
▌ pulsa → o haz clic para empezar
01 el problema

Un LLM no es un equipo.

Hoy trabajamos con los modelos uno a uno: cada persona, su chat, su prompt, su contexto. Eso no escala a un flujo de trabajo real.

  • El contexto se evapora — lo que decidió el modelo que planifica nunca llega al que escribe código.
  • Cero control — el modelo puede leer y escribir lo que quiera, sin límites de coste ni de alcance.
  • Nada es reproducible — el flujo vive en la cabeza de cada dev, no en el repositorio.
  • Un solo modelo para todo — aunque cada tarea tenga un modelo que la hace mejor (y más barato).
02 la idea

Declara el flujo. Orquesta los modelos.

Un pipeline se define en YAML y se versiona con el código: etapas, dependencias, y un modelo distinto para cada etapa, todos trabajando sobre un contexto común.

stage · plan
Planificación
claude-opus-4-5
Analiza requisitos y produce el plan técnico.
stage · code
Desarrollo
gpt-4o
Implementa leyendo el plan desde el contexto.
stage · test
Testing
qwen2.5-coder · local
Genera y ejecuta tests sobre lo implementado.
la analogía: "Kubernetes para agentes de IA" — tú declaras el estado, el orquestador lo ejecuta
03 qué es openthinking

CLI-first, abierto y sin lock-in.

Shell interactiva (REPL)

Ejecutar openthk abre una shell al estilo Claude Code: slash commands para configurar (/pipeline, /providers) y lenguaje natural para ejecutar.

Un binario, cero fricción

TypeScript estricto sobre Bun, compilado a binario único con bun build --compile. SQLite embebido para el contexto. Sin servicios externos.

Cualquier proveedor

18+ proveedores en el catálogo — OpenAI, Anthropic, Google, Mistral, DeepSeek… y modelos locales con Ollama o llama.cpp. Mézclalos en un mismo pipeline.

Del equipo, no de la persona

El pipeline es un fichero YAML en el repo: se revisa en PRs, se versiona y cualquiera del equipo lo ejecuta igual.

04 el pipeline

Todo cabe en un YAML.

Los proveedores se declaran solo por nombre: URLs y API keys se resuelven desde el catálogo y la config global (~/.openthk). Las dependencias entre etapas forman un DAG.

depends_on → orden etapas independientes → paralelo context → permisos
pipeline.yaml
name: review-service
mode: sequential

providers:
  - anthropic   # resuelto del catálogo
  - openai
  - ollama      # modelo local

stages:
  plan:
    provider: anthropic
    model: claude-opus-4-5
    skill: core/arch-planner@1.0
    context: { write: ["plan.*"] }

  code:
    provider: openai
    model: gpt-4o
    skill: core/code-writer@1.0
    depends_on: [plan]
    context:
      read:  ["plan.*"]
      write: ["code.*"]
05 arquitectura

Del YAML a la ejecución.

parser
Parser + validador
Valida el YAML y resuelve cada proveedor a tipo, URL y credenciales.
executor
Executor (DAG)
Ordena etapas por dependencias y ejecuta el agent loop de cada una.
providers
Adaptadores LLM
Interfaz OpenAI-compatible común; adapters para Anthropic y Ollama. Streaming por SSE.
Context store

Clave-valor sobre SQLite con namespaces (plan.architecture) y búsqueda vectorial local. Es la memoria compartida del pipeline.

Policy engine

Se evalúa antes de cada lectura/escritura de contexto: glob matching, rate limits y límites de coste. Transversal a todo.

06 dos modos de ejecución

Plan estático o decisión dinámica.

mode: sequential

El grafo manda

Las etapas se ejecutan según depends_on. Determinista y predecible: ideal para flujos conocidos tipo plan → code → test. Las ramas independientes corren en paralelo.

plan ──▶ code ──▶ test └─▶ docs (en paralelo)
vs
mode: orchestrated

Un LLM dirige

Una etapa con role: orchestrator decide en caliente a qué agente invocar y con qué tarea, mediante la tool delegate(agent, task). Puede repetir agentes, iterar, replanificar.

orchestrator ├─ delegate("architect", …) ├─ delegate("coder", …) └─ delegate("coder", "fix: …")
Ctrl+C cancela el run completo — AbortController propagado a todas las etapas
07 dentro de una etapa

Cada etapa es un agente.

No es una única llamada al modelo: es un bucle iterativo donde el LLM razona, usa herramientas y observa el resultado.

01chat
el modelo recibe skill + contexto
02tool calls
decide qué herramientas usar
03execute
el runtime las ejecuta de verdad
04observe
el resultado vuelve al modelo
↻ se repite hasta terminar o alcanzar max_iterations
read_file write_file list_files run_command search_files delegate · solo orquestador
08 contexto compartido

La memoria del equipo.

Un store clave-valor con namespaces en notación de puntos. Cada etapa declara qué puede leer y qué puede escribir con patrones glob — escribir fuera de tu namespace es un error duro, no una sugerencia.

  • SQLite embebido (bun:sqlite) — sin infraestructura que desplegar.
  • Búsqueda vectorial local con vectra para recuperar contexto por semántica.
  • TTL configurable — el contexto expira, p. ej. 7d.
context store
# namespace · clave            quién escribe
plan.architecture              ← plan
plan.endpoints                 ← plan
code.files                     ← code
code.decisions                 ← code
test.results                   ← test

# permisos de la etapa "code"
read:  ["plan.*"]   # ✓ plan.architecture
write: ["code.*"]   # ✗ test.results → error
09 skills

Comportamiento reutilizable.

Una skill empaqueta el prompt (prompt.md) y su manifiesto (skill.yaml). El manifiesto declara qué herramientas necesita — y eso se aplica en el registry de tools, no en el prompt: si una tool no está permitida, el modelo no puede llamarla por mucho que lo intente.

  • Orden de resolución: YAML del pipeline → manifiesto de la skill → todas las tools.
  • Sin tipos de etapa hardcodeados: cada autor decide qué puede hacer su skill.
skills/arch-planner/skill.yaml
name: arch-planner
version: "1.0"
description: Produce un plan técnico.

context:
  reads:  ["input.*"]
  writes: ["planner.*"]

# enforced a nivel de registry
allowed_tools:
  - read_file
  - list_files
  - search_files
  # sin write_file: solo planifica

constraints:
  min_tokens: 4000
10 políticas

Agentes con autonomía, no con impunidad.

Las políticas se declaran en el YAML y se evalúan en runtime, antes de cada operación. Dar herramientas a un LLM exige poner barandillas.

rate_limit

Límite de peticiones por etapa. Un agente en bucle no puede fundir tu cuota de API.

cost_limit

Coste máximo por run del pipeline. Si se supera, la ejecución se corta — no la factura.

audit_log

Traza de cada lectura, escritura y tool call. Sabes qué hizo cada modelo y cuándo.

misma filosofía que los permisos de contexto: denegar es un error duro, visible y trazable

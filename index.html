01 el problema

Un LLM no es un equipo.

Hoy trabajamos con los modelos uno a uno: cada persona, su chat, su prompt, su contexto. Eso no escala a un flujo de trabajo real.

  • El contexto se evapora — lo que decidió el modelo que planifica nunca llega al que escribe código.
  • Agentes sin frenos — un agente con acceso a tu shell puede ejecutar cualquier cosa, sin revisión ni límites de coste.
  • Nada es reproducible — el flujo vive en la cabeza de cada dev, no en el repositorio.
  • Un solo proveedor para todo — aunque cada tarea tenga un modelo que la hace mejor, más rápido o más barato.
02 la idea

Declara el flujo. Orquesta los modelos.

Un pipeline se define en YAML y se versiona con el código: etapas, dependencias y un modelo distinto para cada etapa, todos trabajando sobre un contexto común y gobernado.

stage · planning
Planificación
claude-opus-4-5
Analiza requisitos y escribe el plan en plan.*
stage · develop
Desarrollo

03 qué es openthinking

CLI-first, abierto y en tu gestor de paquetes.

Shell interactiva (REPL)

Ejecutar openthk abre una shell al estilo Claude Code: slash commands para configurar, autocompletado con Tab, y lenguaje natural para lanzar el pipeline cargado.

Instalación en un comando

npm install -g openthk (o pnpm, o bun) en Windows, macOS y Linux. Sin servicios externos: SQLite embebido para el contexto. Opcionalmente, binario standalone.

Cualquier proveedor

18+ proveedores en el catálogo — OpenAI, Anthropic, Google, Mistral, DeepSeek… y modelos locales con Ollama, LM Studio o llama.cpp. Mézclalos en un mismo pipeline.

Del equipo, no de la persona

El pipeline es un YAML en el repo: se revisa en PRs y cualquiera lo ejecuta igual. El workspace .openthk/ guarda historial y aprendizajes de runs anteriores.

04 el pipeline

Todo cabe en un YAML.

Los proveedores se declaran solo por nombre: URLs y API keys se resuelven desde el catálogo y la config global (~/.openthk, permisos 0600). Las dependencias entre etapas forman un DAG.

depends_on → orden etapas independientes → paralelo context → permisos on_fail → reintentos
openthk.pipeline.yaml
name: feature-development
mode: sequential

providers:
  - anthropic   # resuelto del catálogo
  - openai

stages:
  planning:
    provider: anthropic
    model: claude-opus-4-5
    skill: core/arch-planner@1.0
    context: { write: ["plan.*"] }

  develop:
    provider: openai
    model: gpt-4o
    skill: core/code-writer@1.0
    depends_on: [planning]
    context:
      read:  ["plan.*"]
      write: ["code.*"]
    on_fail:
      retry_stage: planning
      max_retries: 2
05 arquitectura

Del YAML a la ejecución.

parser
Parser + validador
Valida el YAML y resuelve cada proveedor a tipo, URL y credenciales.
executor
Executor (DAG)
Ordena etapas por dependencias y ejecuta el agent loop de cada una, con recuperación de errores.
providers
Adaptadores LLM
Interfaz OpenAI-compatible común; adapters para Anthropic, Azure u Ollama. Streaming por SSE.
Context store

Clave-valor sobre SQLite con namespaces, snapshots y compresión. La memoria compartida del pipeline.

Policy engine

Glob matching, rate limits y límites de coste, evaluados antes de cada operación.

Permissions + sandbox

Cada tool call pasa por el motor de permisos; opcionalmente, todo ocurre en un sandbox aislado.

06 dos modos de ejecución

Plan estático o decisión dinámica.

mode: sequential

El grafo manda

Las etapas se ejecutan según depends_on. Determinista y predecible: ideal para flujos conocidos tipo plan → code → test. Las ramas independientes corren en paralelo.

plan ──▶ code ──▶ test └─▶ docs (en paralelo)
vs
mode: orchestrated

Un LLM dirige

Una etapa con role: orchestrator decide en caliente a qué agente invocar mediante la tool delegate(agent, task). Y tú puedes inyectarle mensajes en vivo mientras trabaja, para corregir el rumbo sin cancelar el run.

orchestrator ├─ delegate("architect", …) ├─ delegate("coder", …) │ ◀ tú: "usa Postgres, no MySQL" └─ delegate("coder", "fix: …")
Ctrl+C cancela el run completo — AbortController propagado a todas las etapas
07 dentro de una etapa

Cada etapa es un agente.

No es una única llamada al modelo: es un bucle iterativo donde el LLM razona, usa herramientas y observa el resultado. Y en vez de acumular todo el historial (que crece cuadráticamente en tokens), el loop mantiene una working memory comprimida: log de acciones + notas del modelo + solo el último intercambio.

03permisos
el motor aprueba, pregunta o deniega
04execute

el resultado vuelve al modelo

08 contexto compartido

La memoria del equipo.

Un store clave-valor con namespaces en notación de puntos. Cada etapa declara qué puede leer y qué puede escribir con patrones glob — escribir fuera de tu namespace es un error duro.

  • SQLite embebido — sin infraestructura que desplegar. Búsqueda vectorial local para recuperar contexto por semántica.
  • Versionado con snapshots — el estado del contexto se captura y se puede restaurar; el executor lo usa para hacer rollback entre reintentos.
  • Compresión transparente — entradas >4 KB se comprimen con gzip sin que las etapas lo noten.
context store
# namespace · clave            quién escribe
plan.architecture              ← planning
code.files                     ← develop
test.results                   ← testing

# permisos de la etapa "develop"
read:  ["plan.*"]   # ✓ plan.architecture
write: ["code.*"]   # ✗ test.results → error

# el estado se versiona con snapshots
snapshot: auto · pre-stage · restaurable
09 seguridad · permisos

Human-in-the-loop, como en Claude Code.

Cada tool call pasa por un motor de permisos con un clasificador de riesgo: leer es safe, escribir en el workspace es moderate, y rm, sudo o escribir fuera del proyecto es dangerous. Puedes responder "permitir siempre" o "denegar siempre" y la regla se persiste.

auto

Todo se permite. Para pipelines de confianza y CI.

sandbox

Los agentes trabajan en un entorno aislado; tú revisas el diff al final.

confirm

Lo seguro pasa solo; lo demás espera tu aprobación en CLI o UI.

strict

Toda acción requiere confirmación explícita. Máximo control.

las solicitudes llegan al Permission Center de la UI o al prompt del REPL — donde estés
10 seguridad · sandbox

Deja que el agente trabaje. Revisa el diff.

En modo sandbox, las escrituras y comandos ocurren en un directorio temporal que replica tu proyecto. Las lecturas caen al filesystem real (con prioridad para el overlay del sandbox), así el agente ve tu código pero no lo toca.

  • Al terminar, ves un diff por fichero: añadido, modificado o borrado — y decides aplicar o descartar.
  • Protección de escape — los paths se resuelven y validan: ni symlinks ni ../ sacan al agente de su jaula.
sandbox review
# run terminado — cambios pendientes
+ added     src/api/users.ts
~ modified  src/router.ts
~ modified  src/db/schema.ts
- deleted   src/legacy/users.js

aplicar cambios? [a]pply / [d]iscard / [r]eview
11 resiliencia

Los fallos son parte del plan.

Un pipeline real falla: APIs caídas, rate limits, modelos que se equivocan. El executor trata el error como un estado más, no como el final.

Retry con backoff

Reintentos con backoff exponencial y jitter, por etapa y por petición al proveedor.

Rollback de contexto

Antes de cada etapa se hace un auto-snapshot; entre reintentos, el contexto vuelve a ese punto limpio.

Fallback de modelo

Si un modelo agota su rate limit, la petición salta al siguiente de la cadena de fallback.

Pause-on-error

El run se pausa y te pregunta: retry, skip o abort. Tú decides, no el stack trace.

además, on_fail.retry_stage puede relanzar una etapa anterior inyectándole el detalle del fallo — un feedback loop declarativo
12 costes

Saber cuánto cuesta antes de que duela.

Cada etapa acumula tokens de entrada y salida, y una tabla de precios por modelo (actualizada a mayo de 2026) los convierte en dólares. En modo orquestado, el coste de cada delegate se atribuye a su agente.

  • cost_limit: "$50/run" — si el run supera el límite, se corta con COST_EXCEEDED. La factura no se entera.
  • Sin números inventados — modelo desconocido: se intenta por prefijo y, si no hay match, el coste es null, nunca una estimación falsa.
  • Audit log — traza de cada lectura, escritura y tool call, exportable desde la UI.
